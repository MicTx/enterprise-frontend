# 为什么参考驱动:让 agent 改造现有页面,而不是从零生成

让 AI agent 在公司仓库里加后台页面,结果常常是:页面能跑,风格是别人的。enterprise-frontend 反着来:先在目标仓库里找一条走得通的同类旅程,照着它改。这篇拆开它的四个部件——纵切片、来源优先级、最小完整改动、交付门——说明每个为什么长这样。

## 从零生成的页面,为什么活不下来

从零生成不是能力问题。模型写得出一个功能齐全的 CRUD 页面;麻烦在于存量仓库的验收标准不是「功能齐全」,而是「像这个仓库的页面」。

死因有三。平行基建:agent 新建一套请求封装和状态管理,与既有的一套并行。约定漂移:命名、目录、权限、反馈,各仓库写法不同,通用规则猜不中。评审成本:能跑不等于能合入,评审者要逐处核对偏离。

差异能逐行检出,改起来不贵,前提是 agent 知道按谁的规矩改。「像这个仓库」的证据就在仓库身上,缺的是把它变成 agent 施工依据的方法——这套方法叫参考驱动:证据取自目标仓库,而非通用规则。

## 照什么改:纵切片

参考不是单个组件,而是一条完整的用户旅程。**纵切片**(vertical slice,也译垂直切片)是一条用户旅程从头到尾的全部代码:路由和菜单入口、权限、界面、数据请求与状态、加载/空/错误的反馈,以及测试。组件只回答「长什么样」;旅程还回答「怎么到达、谁能用、出错怎么办」——照组件抄,这些答案要 agent 自己编;照旅程改,答案已在参考里。

最小例:仓库已有客户管理页,要新增供应商管理。两者是同一类旅程——列表、检索、新建、编辑、停用,数据形态和权限模型同构。agent 把客户管理的纵切片当模板,路由怎么注册、权限怎么判断、请求怎么封装、表格怎么配置,逐层对照着改,新页面从第一天起就「像这个仓库」。

临帖是它的日常版本:学书法先临帖,不是先读笔法再闭门创作。类比只到「照着做」为止:临帖复制外形,这里要换掉数据模型和业务语义,保留结构与约定。

挑参考按用户任务与交互、数据生命周期的贴近程度排,不按外观相似;没有同类旅程时,退一步用目标仓库基础件拼装,显式写下缺失契约,不整体移植不兼容的子系统。

## 参考打架时听谁的:来源优先级

参考常互相冲突:用户说的和代码写的不一致,内置资料和已装版本对不上。**来源优先级**(source precedence)给冲突定了顺序:

| 顺序 | 来源 |
|---|---|
| 1 | 用户当前请求与显式约束 |
| 2 | 目标仓库的代码、配置、测试与本地说明 |
| 3 | 用户提供的参考仓库、页面、截图或设计 |
| 4 | 目标仓库内最接近的成熟示例 |
| 5 | 框架文档与可运行示例 |
| 6 | 内置默认,只兜底未决的选择 |

两个要点:截图不覆盖可执行的行为——界面长得像参考,行为仍以仓库为准;内置默认只回答「仓库没有答案的问题」,不拿来做合规检查,目标仓库的主题、路由、请求、权限、命名,除非用户要求或确有必要,不让外部参考替换。

## 改到哪里为止:最小完整改动

参考找到了,改动收敛在哪?**最小完整改动**有两半,缺一半都出问题。

「最小」管范围:局部修复就是局部修复,不借机做仓库普查,不把修 bug 升级成迁移。范围由受影响的行为决定——沿着 import、调用方和状态转移走到边界为止,不相干的层不看。反例:修一个按钮换行,顺手重排整页滚动,评审者要为没要求的变化买单。

「完整」管交付。新旅程必须整条可用:缺权限,点了报错;缺空态,首屏白板;缺失败反馈,用户不知道存没存——哪一环缺了都是「看起来完成、实际不可交付」。

一句话:对既有约定做最小的让步,对用户旅程做完整的交付。

## 怎么确认没改坏:交付门

改编最容易翻车的不是功能,是证据:agent 说「改好了」,依据是什么?**交付门**(Final Gate)要求返回前过四道检查:

1. 请求的行为与相关状态满足,且没有替换无关的既有约定;
2. 聚焦的测试与仓库要求的检查通过;
3. UI 的交互与几何尺寸在可运行时实际操作过——编译通过不算 UI 证据;
4. diff 里没有源残留、平行基建或生成的本地文件。

后两条是改编特有的:从模板改出来的代码,最容易留下模板残渣——源仓库的路由名、角色、接口、样式类。残渣编译不报错,单测也不覆盖,只有实际操作界面、看 diff 才暴露。把「操作过」而非「编译过」设为证据标准,是对「页面能跑,风格是别人的」的最后一道拦截。

边界也要说清:参考驱动不是万金油。探索性原型、没有参考对象的全新设计,生成式做法仍然合适;仓库乱到无约定可循时,先用 Adopt 模式整理地基,再谈改编。方法是固定的,判断力在每次挑参考的现场——这也是它像熟手、不像规范的原因。
